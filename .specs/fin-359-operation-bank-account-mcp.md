# Банковский счёт на операции в MCP

**Статус:** Утверждено (2026-08-29, rev.3).

## Назначение

- Операторы на пути только через MCP не читают, не фильтруют и не записывают банковский счёт на заголовке операции без обхода сырым HTTP.
- Нужен паритет существующих инструментов MCP с HTTP-поверхностью банковского счёта на операции.

## Входит в объём

- Расширение выборки операций идентификатором банковского счёта на заголовке.
- Фильтр выборки операций по идентификатору банковского счёта, включая sentinel отсутствия счёта.
- Чтение идентификатора банковского счёта в ответе чтения операции.
- Запись идентификатора банковского счёта через каноническое частичное обновление операции.
- Возврат идентификатора банковского счёта в успешном ответе частичного обновления и фасада классификации.
- Отклонение ключа банковского счёта во входе фасада классификации схемой MCP до HTTP.
- Проброс доменных ошибок записи банковского счёта в ошибку инструмента.
- Обновление справочника доступных инструментов MCP.

## Вне объёма

- Модель, миграция схемы и слой сохранения банковского счёта на операции (FIN-245).
- Программный интерфейс HTTP банковского счёта на операции (FIN-358).
- Пользовательский интерфейс банковского счёта на операции (FIN-360).
- Заполнение банковского счёта при импорте (FIN-288).
- Начальное заполнение существующих операций (FOPS-30).
- Запрет sentinel фильтра как идентификатора в справочнике банковских счетов (FIN-362).
- Отдельный инструмент MCP для ответа filter-choices списка операций.
- Отдельный инструмент MCP для HTTP-фасада проекта: запись проекта остаётся в каноническом частичном обновлении.
- Поле платёжного инструмента на операции.
- Запись банковского счёта на позиции операции.
- Новый инструмент создания операции через MCP.
- Изменение агрегата плана и факта из банковского счёта.

## Текущее поведение

| Область | Текущее поведение | Проблема |
| ------- | ----------------- | -------- |
| Выборка операций | Строка собирается из ограниченного набора полей без банковского счёта; фильтра по счёту нет | Оператор не видит и не отбирает операции по счёту |
| Чтение операции | Тело HTTP передаётся без гарантии ключа банковского счёта в норме MCP | После FIN-358 поле есть в HTTP, но норма MCP его не фиксирует |
| Частичное обновление | Объявленный набор полей и белый список ответа без банковского счёта | Оператор не назначает счёт через MCP; успешный ответ поле теряет |
| Фасад классификации | Вход и белый список ответа без банковского счёта | HTTP отдаёт счёт в ответе; MCP его отбрасывает |
| `mcp-gaps.md` | Строки выборки и частичного обновления без банковского счёта на операции | Label `mcp-gap` на FIN-359 |

## Целевое поведение

#### Паритет поверхности (D-01)

- Набор инструментов операций не расширяется и не сужается.
- Эта задача не добавляет инструмент создания операции.
- Норма полного набора CRUD для нового ресурса к этой задаче не применяется.
- Эта задача расширяет уже существующие инструменты полями и фильтром уже существующего HTTP-контракта FIN-358.
- Поверхность плана и факта этой задачей не меняется.
- Отдельный инструмент для `GET /api/v1/transactions/filter-choices` не вводится: опции фильтра для UI остаются HTTP-поверхностью FIN-358; ops используют фильтр выборки и справочник счетов.
- Отдельный MCP-инструмент HTTP-фасада проекта не вводится: запись проекта и банковского счёта выполняется через каноническое частичное обновление.

| Инструмент MCP | Операция HTTP | Что меняется |
| -------------- | ------------- | ------------ |
| `query_transactions` | `GET /api/v1/transactions` | Идентификатор банковского счёта в каждой неагрегированной строке; опциональный фильтр `bank_account_id` |
| `get_transaction` | `GET /api/v1/transactions/{transaction_id}` | Идентификатор банковского счёта в заголовке |
| `put_transaction` | `PATCH /api/v1/transactions/{transaction_id}` | Приём и ответ с идентификатором банковского счёта |
| `put_transaction_category` | `PATCH /api/v1/transactions/{transaction_id}/category` | Идентификатор банковского счёта только в ответе; вход его не принимает |

- Доменные правила банковского счёта на операции наследуются из FIN-245 и FIN-358 без дублирования формулы в MCP.

#### Конвейер (D-02)

```
1. получить сессию API (профиль данных, базовый URL)
2. проверить аргументы MCP до HTTP, если инструмент это уже делает
3. выполнить существующий вызов HTTP без новых маршрутов
4. при ожидаемом коде HTTP успеха сформировать ответ с банковским счётом согласно D-04…D-07
5. иначе вернуть ошибку инструмента с телом ответа API
6. сетевые сбои пробросить без дополнительной обёртки
```

- Порядок шагов совпадает с существующими обработчиками этих инструментов.
- MCP не выводит банковский счёт из канала импорта и не подставляет значение из других полей.

#### Модули и регистрация (D-03)

- Расширение выборки и фильтра выполняется в существующем `scripts/query-transactions.py` и в обработчике `query_transactions`.
- Обеспечение ключа банковского счёта при чтении операции выполняется в существующем `scripts/get_transaction.py`.
- Приём и возврат поля в частичном обновлении выполняются в существующем `scripts/put_transaction.py`.
- Возврат поля в фасаде классификации выполняется в существующем `scripts/put_transaction_category.py`.
- Схемы инструментов обновляются в `server.py`.
- В рамках реализации в `mcp-gaps.md` у строк `query_transactions`, `get_transaction`, `put_transaction` и `put_transaction_category` явно указывается поддержка `bank_account_id` на операции (чтение, фильтр, запись и ответ) со ссылкой **FIN-359** ✓; отдельная строка gap по банковскому счёту на операции не остаётся.
- Label `mcp-gap` снимается с FIN-359 при переводе задачи в Done и не входит в критерий функциональной приёмки.

#### Выборка операций (D-04)

##### Состав неагрегированной строки

- Неагрегированная строка всегда содержит ключ идентификатора банковского счёта (`bank_account_id`).
- Ключ `payment_instrument_id` на строке операции не добавляется.

| Поле | Описание | Норма |
| ---- | -------- | ----- |
| `bank_account_id` | Банковский счёт операции | Значение `bank_account_id` из HTTP без преобразования; если ключ в HTTP отсутствует, JSON `null` |

- MCP не валидирует и не нормализует значение сверх того, что уже делает передача в HTTP-фильтр.
- Пустая строка для этого ключа в ответе MCP не используется, если HTTP отдал JSON `null`.

##### Фильтр

- Инструмент `query_transactions` принимает опциональный аргумент `bank_account_id`.
- Для переданного значения выполняется `strip`; нормализованное значение уходит в query HTTP.
- Отсутствие аргумента или пустая строка после нормализации не накладывает фильтр по банковскому счёту.
- Sentinel отсутствия счёта равен `__empty__` и передаётся в HTTP как есть.
- Семантика фильтра, сочетание с другими фильтрами и пустой список при неизвестном счёте наследуются из FIN-358 без изменения на слое MCP.
- Аргумент `bank_account_id` учитывается в правиле «есть ли активный фильтр» наравне с прочими строковыми фильтрами выборки: непустое нормализованное значение само по себе допускает запуск списка.

##### Агрегация по месяцу

- Агрегация по месяцу сохраняет прежнюю семантику.
- Агрегированная строка `query_transactions` не содержит ключ `bank_account_id`.

##### Пример неагрегированной строки

```json
{
  "id": "aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee",
  "date": "15.07.2026",
  "amount": 10.0,
  "indicator": "D",
  "category": "C0001",
  "transaction_type": "C",
  "expense_owner": null,
  "fund_id": null,
  "provider": "tbank",
  "bank_account_id": "acc-tbank-rub",
  "description": "Card purchase",
  "currency": "EUR",
  "budget_currency": "EUR",
  "planned_rate": null,
  "posted_amount": "10.00",
  "posted_currency": "EUR"
}
```

##### Пример фильтра операций без счёта

- Вызов `query_transactions` с `bank_account_id` равным `__empty__` и иным допустимым фильтром периода.
- В каждой возвращённой неагрегированной строке `bank_account_id` равен JSON `null`.

#### Чтение операции (D-05)

- Успешный `get_transaction` всегда включает ключ `bank_account_id` в объекте операции.
- Если HTTP вернул ключ, MCP копирует его значение без изменения.
- Если ключ в HTTP отсутствует, MCP отдаёт JSON `null` для этого ключа.
- MCP не отбрасывает присутствующий ключ и не подставляет значение из `provider` или иных полей.
- Банковский счёт относится только к заголовку: позиции операции собственного ключа не получают.
- Ключ `payment_instrument_id` на операции не добавляется.

##### Пример фрагмента операции

```json
{
  "ok": true,
  "profile": "cand",
  "base": "http://127.0.0.1:8001",
  "transaction": {
    "id": "aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee",
    "provider": "tbank",
    "bank_account_id": "acc-tbank-rub",
    "fund_id": null
  }
}
```

#### Частичное обновление (D-06)

##### Вход

- Объявленный набор полей тела `put_transaction` дополняется ключом `bank_account_id`.
- Тип аргумента `bank_account_id` в схеме MCP: `string` или JSON `null`.
- Четыре состояния входа к HTTP-телу:

| Вход MCP | HTTP body | Результат на стороне API |
| -------- | --------- | ------------------------ |
| ключ отсутствует | ключ отсутствует | банковский счёт не изменяется |
| `bank_account_id: null` | `"bank_account_id": null` | отказ `bank_account_required` |
| строка, пустая после `strip` | `"bank_account_id": ""` | отказ `bank_account_required` |
| непустая строка после `strip` | `"bank_account_id": "<нормализованный id>"` | назначение счёта или иной доменный отказ FIN-358 |

- Ключ, отсутствующий в аргументах, не попадает в JSON тела запроса.
- Ключ со значением `null` уходит в JSON как `null` и не означает «ключ отсутствует».
- Непустое строковое значение после `strip` уходит в тело; пробелы по краям не сохраняются: `"  acc-c24  "` даёт тело `"acc-c24"`.
- Пустая строка после `strip` уходит в тело как пустая строка и не преобразуется MCP в `null`.
- Значение `__empty__` уходит в HTTP без специальной ветки MCP.
- Условная обязательность «хотя бы одно поле из объявленного набора» включает `bank_account_id`.
- Параметр `allow_closed` сохраняет прежнюю семантику.

##### Ответ

- Белый список ответа `put_transaction` дополняется ключом `bank_account_id`.
- Если ключ отсутствует в HTTP, в успешном ответе MCP значение равно JSON `null`.
- Ключ `payment_instrument_id` в ответ не добавляется.

##### Пример назначения счёта

```json
{
  "transaction_id": "aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee",
  "bank_account_id": "acc-c24"
}
```

##### Пример нормализации пробелов

```json
{
  "transaction_id": "aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee",
  "bank_account_id": "  acc-c24  "
}
```

- Запись успешна; чтение возвращает `acc-c24`.

#### Фасад классификации (D-07)

##### Вход

- Схема `put_transaction_category` не объявляет аргумент `bank_account_id`.
- Незаявленные аргументы верхнего уровня по-прежнему отклоняются схемой MCP до HTTP.
- HTTP при таком входе не вызывается.
- Отказ отличается от ошибки API: это ошибка схемы MCP (например, текст про `Additional properties are not allowed`), а не сообщение с кодом HTTP и путём API.

##### Ответ

- Белый список ответа `put_transaction_category` дополняется ключом `bank_account_id`.
- Если ключ отсутствует в HTTP, в успешном ответе MCP значение равно JSON `null`.

#### Ошибки записи (D-08)

- FIN-359 не вводит собственных кодов ошибок банковского счёта на слое MCP.
- Доменные коды FIN-358 на пути канонической записи пробрасываются в ошибку инструмента вместе с кодом HTTP и телом ответа API.
- Форма ошибки инструмента для ответа API включает код HTTP, доменный `error.code` и исходное тело ответа API (или его эквивалент в существующем формате `format_api_error`); потеря любого из этих элементов запрещена.

| Ситуация | Источник | Поведение |
| -------- | -------- | --------- |
| Ключ передан со значением `null` либо строкой, пустой после нормализации | API | ошибка инструмента; код `bank_account_required` |
| Значение `__empty__` во входном теле канонического пути | API | ошибка инструмента; код `validation_error` |
| Счёт не найден в активном профиле | API | ошибка инструмента; код `bank_account_not_found` |
| Учётный период закрыт и `allow_closed` равен лжи | API | ошибка инструмента; код `period_closed` |
| Аргумент `bank_account_id` во входе `put_transaction_category` | MCP до HTTP | отклонение схемой MCP; HTTP не вызывается |
| Прочие ошибки частичного обновления и классификации | API | без изменения формы ошибки инструмента |
| HTTP status чтения или выборки не равен ожидаемому успеху | MCP | ошибка инструмента с телом API |
| Transport / network | HTTP-клиент | исключение без дополнительной обёртки |

- Отсутствие ключа `bank_account_id` в аргументах `put_transaction` не является ситуацией этой таблицы: ключ не попадает в тело, счёт не меняется (D-06).
- После отказа API состояние банковского счёта операции не изменяется.
- MCP не разбирает `error.code`, чтобы выбрать иной исход, кроме ошибки инструмента.
- Отказ HTTP с кодом 422 и кодом ошибки `validation_error` при ключе банковского счёта во входном теле фасада классификации через MCP не воспроизводится: схема отклоняет ключ до HTTP.

#### Обратная совместимость (D-09)

- Вызов `query_transactions` без аргумента `bank_account_id` сохраняет значения и семантику ранее существовавших полей строки и прежних фильтров.
- Добавление ключа `bank_account_id` в строку выборки и в успешные ответы частичного обновления и фасада классификации является расширением тела.
- Вызывающая сторона, которая неизвестные ключи ответа игнорирует, продолжает разбирать прежние поля этих инструментов.
- Агрегация выборки по месяцу не меняется и не получает ключ `bank_account_id`.
- Схемы инструментов не получают новых обязательных аргументов.
- Контракт HTTP FIN-358 этой задачей не меняется.
- План и факт через `query_plan_fact` не меняется.

#### Инварианты (D-10)

- После успешной неагрегированной выборки у каждой строки есть ключ `bank_account_id`.
- После успешного чтения операции в объекте операции есть ключ `bank_account_id`.
- После успешного частичного обновления и успешного фасада классификации в объекте `transaction` есть ключ `bank_account_id`.
- Агрегированная строка выборки не содержит этот ключ.
- Ни один изменяемый этой задачей ответ операции не содержит ключ `payment_instrument_id`.
- MCP не считает чтение или запись успешными при коде HTTP, отличном от ожидаемого успеха инструмента.

## Предположения, предусловия и ограничения

- HTTP-поверхность FIN-358 доступна на профиле приёмки: чтение, фильтр и запись банковского счёта на операции уже работают по утверждённому контракту.
- Миграция схемы с колонкой банковского счёта на операции применена (FIN-245).
- Приёмка фильтра `__empty__` на `cand` допустима до Done FIN-362, если в справочнике банковских счетов профиля нет идентификатора `__empty__` и это зафиксировано в метаданных прогона.
- Release gate FIN-358 на FIN-362 наследуется этой задачей: выпуск и развёртывание функциональности банковского счёта на операции через MCP не считается безопасным при незакрытом FIN-362, даже если приёмка на `cand` прошла без коллизии.

## Критерий приёмки

- Чтение операций через MCP возвращает идентификатор банковского счёта согласно целевому поведению.
- Выборка операций через MCP допускает фильтрацию по идентификатору банковского счёта согласно целевому поведению.
- Через MCP можно назначить банковский счёт на операции каноническим частичным обновлением согласно целевому поведению.
- Доменные ошибки записи банковского счёта отображаются в ошибке инструмента без потери кода HTTP, доменного `error.code` и тела ответа API.
- Успешный ответ фасада классификации через MCP содержит идентификатор банковского счёта; вход фасада ключ не принимает.
- В ответах изменяемых этой задачей инструментов нет поля платёжного инструмента на операции.
- В `mcp-gaps.md` у инструментов операций указана поддержка `bank_account_id` со ссылкой **FIN-359** ✓.
- Поведение покрыто функциональными тестами.

## Функциональное тестирование

Норма оформления: `FinancePlanningProject/standards/specs/testing/functional-testing.md`.

### Предусловия

- Проверочные действия T1–T4 выполняются через MCP `finance_api_connect` с профилем данных `cand` на постоянной `finance.db` приложения, не на временной SQLite.
- Все операции, которые прогон читает или изменяет для T1–T4, создаются как фикстуры этого прогона через слой сохранения или HTTP; существующие операции профиля не переиспользуются.
- Фикстура без счёта для T1.4 и T4.3 создаётся со значением `bank_account_id`, равным `null`, через слой сохранения и удаляется вместе с остальными фикстурами прогона.
