# Массовое частичное обновление операций через MCP

**Статус:** Утверждено (2026-08-30, rev.4).

## Назначение

- Оператор не может применить каноническое частичное обновление сразу к нескольким операциям одним вызовом MCP и вынужден вызывать инструмент по одной строке.
- Нужен один инструмент MCP для пакетной записи по тому же контракту полей, что у одиночного частичного обновления операции.

## Входит в объём

- Один новый инструмент MCP пакетного частичного обновления операций.
- Элемент пакета с идентификатором операции и тем же набором omit / null полей, что у одиночного инструмента частичного обновления.
- Единый источник определения полей тела для одиночного и пакетного инструментов.
- Общий для пакета параметр обхода защиты закрытого учётного периода.
- Ответ с результатом по каждому элементу пакета.
- Повторное использование валидации и HTTP-пути одиночного частичного обновления без параллельного пути записи.
- Обновление справочника доступных инструментов MCP.
- Функциональные и модульные тесты смешанного успеха, отказа пустого пакета, валидации элемента до HTTP, повторяющихся идентификаторов, продолжения после сетевой ошибки, общего `allow_closed` на двух операциях и назначения / сброса идентификатора фонда.

## Вне объёма

- Замена узких пакетных поверхностей типа с категорией и только проекта (FIN-213, FIN-130).
- Пакетное частичное обновление в пользовательском интерфейсе.
- Повторный прогон миграции владельца операции в идентификатор фонда (FOPS-19).
- Отдельный HTTP-путь пакетного частичного обновления операций.
- Изменение семантики одиночного инструмента частичного обновления операции.
- Дублирование доменных правил классификации, проекта, фонда и банковского счёта в MCP.
- Транзакционный откат уже применённых элементов пакета при ошибке последующего элемента.
- Отдельное поле `error_code` в результате элемента: код ошибки остаётся частью строки `error`.
- Жёсткий прикладной лимит размера пакета и гарантия продолжительности вызова.
- Автоматический повтор PATCH после сетевой ошибки.

## Текущее поведение

| Область | Текущее поведение | Проблема |
| ------- | ----------------- | -------- |
| MCP запись | `put_transaction` обновляет одну операцию за вызов | Пакет из десятков строк требует столько же вызовов инструмента |
| HTTP | Канонический `PATCH /api/v1/transactions/{id}` без пакетного пути | Нет HTTP-batch для того же контракта |
| Узкие пакеты | В бэклоге есть узкие пакеты типа+категории и только проекта | Они не покрывают канонический набор полей с идентификатором фонда |

## Целевое поведение

#### Инструмент (D-01)

- Инструмент MCP называется `put_transactions`.
- Инструмент является пакетной MCP-поверхностью записи полей операций поверх контракта FIN-258 / FIN-260.
- Одиночный инструмент `put_transaction` сохраняется без изменения семантики.

#### Способ исполнения (D-02)

- Пакет исполняется оркестрацией на стороне MCP: для каждого элемента выполняется тот же канонический `PATCH /api/v1/transactions/{transaction_id}`, что и у `put_transaction`.
- Отдельный HTTP-путь пакетного обновления в этой задаче не вводится.
- Доменные инварианты не дублируются в MCP.

#### Конвейер (D-03)

```
1. схема MCP отклоняет невалидный вызов до обработчика (D-05)
2. проверить аргументы пакета до разрешения сессии (D-05)
3. разрешить профиль данных, сессию API и базовый URL (как у put_transaction)
4. при ошибке шага 3 вернуть ошибку всего инструмента без results (D-12)
5. для каждого элемента по порядку списка:
   a. проверить элемент до HTTP (D-06)
   b. при ошибке до HTTP зафиксировать результат элемента и перейти к следующему
   c. иначе выполнить PATCH с общим allow_closed пакета
   d. при успехе HTTP зафиксировать результат элемента с объектом операции
   e. при ошибке HTTP или сети зафиксировать результат элемента с текстом ошибки и перейти к следующему
6. вернуть конверт успеха инструмента с результатами по всем элементам (D-09)
```

- Порядок элементов фиксирован: слева направо по массиву `items`.
- Ошибка одного элемента не останавливает обработку остальных.
- Повторные попытки после доменной или сетевой ошибки элемента не выполняются.
- Локально невалидный пакет отклоняется одинаково и не требует разрешения API-сессии.

#### Модуль, схема полей и регистрация (D-04)

- Логика пакета размещается в `scripts/put_transactions.py`.
- Построение тела, путь, `allow_closed`, разбор ответа успеха и объявленный набор полей тела переиспользуют модуль одиночной записи без копирования правил полей.
- Схема свойств полей тела элемента `put_transactions` строится из того же общего определения, из которого строится схема полей тела `put_transaction`; ручное дублирование списка свойств полей тела в двух независимых схемах запрещено.
- Обработчик и схема инструмента регистрируются в `server.py`.
- Модульный тест контракта сравнивает нормализованные определения свойств полей тела схем `put_transaction` и элемента `put_transactions.items[]` целиком; различия допускаются только если они явно перечислены в этой спецификации.

#### Уровни отклонения и валидация пакета (D-05)

| Уровень | Когда срабатывает | Результат |
| ------- | ----------------- | --------- |
| Схема MCP | До запуска обработчика | Вызов инструмента отклоняется целиком; `results` не формируется |
| Валидация пакета | В обработчике до разрешения сессии и до цикла по элементам | Исключение инструмента; HTTP не вызывается; `results` не формируется |
| Валидация элемента | В цикле по элементу до HTTP | `results[i].ok = false`; остальные элементы продолжают обрабатываться |
| Backend / сеть | На PATCH элемента | `results[i].ok = false`; остальные элементы продолжают обрабатываться |

##### Схема MCP (отклонение всего вызова)

- Отсутствует ключ `items`.
- Значение `items` не является массивом.
- Элемент `items` не является объектом.
- Тип верхнеуровневых `profile`, `base`, `allow_closed` не соответствует схеме, если ключ передан.
- Тип переданного ключа объявленного набора полей тела внутри элемента не соответствует общей схеме полей (те же типы, что у `put_transaction`).
- Ключ `transaction_id` передан со значением не типа `string`, включая `null`, число и объект: вызов отклоняется схемой целиком.
- Неизвестный ключ на верхнем уровне или внутри элемента при `additionalProperties: false`.

##### Валидация пакета в обработчике

- Массив `items` после прохождения схемы пуст: `ValueError` без разрешения сессии и без вызова API.
- Повторяющиеся идентификаторы операций в одном пакете допускаются: каждый элемент обрабатывается отдельно в своём порядке.

##### Не относят к схеме MCP как обязательные

- Ключ `transaction_id` внутри элемента не входит в `required` схемы элемента: отсутствие ключа обрабатывает валидация элемента (D-06).
- Условная обязательность «хотя бы одно поле тела» не выражается схемой элемента и обрабатывается валидацией элемента (D-06).

#### Валидация элемента до HTTP (D-06)

- Для каждого элемента применяются те же правила валидации полей тела, что у `put_transaction`, включая omit / null; ошибки, отнесённые D-05 к уровню элемента, преобразуются в `results[i].ok = false`, а не в исключение всего инструмента.
- Отсутствие ключа `transaction_id` или пустая строка после `strip` дают `results[i].ok = false` без HTTP для этого элемента.
- Значение `transaction_id: null` к уровню элемента не относится: его отклоняет схема MCP (D-05).
- Отсутствие всех ключей объявленного набора полей тела даёт `results[i].ok = false` без HTTP для этого элемента.
- Сочетаемость полей и доменные проверки выполняет только backend на каждом PATCH.

#### Параметр закрытого периода (D-07)

- Параметр `allow_closed` задаётся один раз на весь пакет.
- Значение по умолчанию равно `false`.
- Семантика совпадает с одиночным `put_transaction`.
- Отдельный `allow_closed` на элементе не вводится.

#### Вход (D-08)

##### Параметры вызова

| Поле | Тип | Обяз. | Описание |
| ---- | --- | ----- | -------- |
| `profile` | string | нет | Профиль данных; по умолчанию из сессии или `prod` |
| `base` | string | нет | Базовый URL API; по умолчанию из сессии |
| `allow_closed` | bool | нет | Обход защиты закрытого учётного периода для всех элементов; по умолчанию `false` |
| `items` | array | да | Список элементов пакета; непустой после валидации пакета |

##### Элемент `items[]`

| Поле | Тип | Обяз. | Описание |
| ---- | --- | ----- | -------- |
| `transaction_id` | string | нет в схеме; да в D-06 | Идентификатор операции; `null` и не-string отклоняет схема MCP |
| поля тела | как у `put_transaction` | условно | Тот же объявленный набор из общего определения (D-04); хотя бы одно поле обязательно по D-06 |

#### Результат успеха инструмента (D-09)

- Инструмент возвращает структурированный ответ без исключения, если валидация пакета (D-05) и разрешение сессии (D-03 шаг 3) прошли и конвейер обработал все элементы.
- Ответ содержит `ok: true`, профиль данных, базовый URL, сводку и массив `results` в том же порядке, что `items`.
- Сводка содержит числа: всего элементов, успешных, с ошибкой.
- Верхнеуровневый `ok: true` означает, что пакет обработан; ошибки отдельных элементов отражаются только в `results` и `summary` и не переводят ответ в ошибку инструмента.

##### Элемент `results[]` при успехе

| Поле | Тип | Описание |
| ---- | --- | -------- |
| `ok` | bool | `true` |
| `transaction_id` | string | Идентификатор из элемента |
| `transaction` | object | Тот же белый список полей, что у успешного `put_transaction` |

##### Элемент `results[]` при ошибке

| Поле | Тип | Описание |
| ---- | --- | -------- |
| `ok` | bool | `false` |
| `transaction_id` | string | Идентификатор из элемента, если удалось его прочитать; иначе пустая строка |
| `error` | string | Текст ошибки до HTTP или текст ошибки API / сети в том же формате, что у одиночной записи; при доменной ошибке API строка включает код ошибки (например `unknown_fund`, `period_closed`) |

- Отдельное поле `error_code` не вводится.
- Для HTTP 4xx значение `ok: false` означает, что API отклонил изменение и успешный ответ не получен.
- Для сетевой ошибки значение `ok: false` означает отсутствие подтверждённого успешного ответа, а не гарантию отсутствия изменения на стороне API. Фактическое состояние операции после отправки PATCH при обрыве соединения может быть неопределённым. Автоматический повтор не выполняется.

```json
{
  "ok": true,
  "profile": "cand",
  "base": "http://127.0.0.1:8001",
  "summary": {
    "total": 2,
    "succeeded": 1,
    "failed": 1
  },
  "results": [
    {
      "ok": true,
      "transaction_id": "<uuid-1>",
      "transaction": {
        "id": "<uuid-1>",
        "fund_id": "personal.elizarov.2026-08"
      }
    },
    {
      "ok": false,
      "transaction_id": "<uuid-2>",
      "error": "PATCH /api/v1/transactions/<uuid-2> -> HTTP 404 unknown_fund: ..."
    }
  ]
}
```

#### Инварианты (D-10)

- Число элементов `results` равно числу элементов `items`.
- Порядок `results` совпадает с порядком `items`.
- `summary.total` равен числу элементов `items`.
- `summary.total` равен сумме `summary.succeeded` и `summary.failed`.
- `summary.succeeded` равен числу элементов `results` с `ok: true`.
- `summary.failed` равен числу элементов `results` с `ok: false`.
- Успешный элемент означает ровно один подтверждённый успешный канонический PATCH для этой позиции списка.
- MCP не выполняет поиск фонда, категории, проекта, счёта или члена домохозяйства до вызова HTTP.
- Уже применённые успешные элементы не откатываются при ошибке последующих.
- Нормализованные определения свойств полей тела схем `put_transaction` и элемента пакета совпадают полностью согласно D-04.

#### Обратная совместимость (D-11)

- Новый инструмент добавляется без изменения семантики `put_transaction` и прочих существующих инструментов MCP.
- Существующие функциональные тесты прочих инструментов не регрессируют.

#### Ошибки (D-12)

| Ситуация | Уровень | Поведение MCP |
| -------- | ------- | ------------- |
| Нарушение схемы MCP из D-05, включая `transaction_id: null` | схема MCP | Вызов отклоняется целиком до обработчика; `results` не формируется |
| Пустой `items` | валидация пакета | `ValueError` до разрешения сессии; HTTP не вызывается; `results` не формируется |
| Ошибка разрешения профиля, сессии или базового URL | до цикла | Ошибка всего инструмента так же, как у `put_transaction`; `results` не формируется |
| Нет ключа `transaction_id`, пустая строка после `strip`, нет полей тела | валидация элемента | `results[i].ok = false`; остальные элементы продолжают обрабатываться |
| Операция не найдена | HTTP 404 | `results[i].ok = false`; строка `error` в формате одиночной записи |
| Доменные ошибки FIN-258 / FIN-260 | HTTP 4xx | `results[i].ok = false`; строка `error` включает код ошибки API |
| Прочий неуспешный HTTP-ответ PATCH, включая 401, 403, 5xx | HTTP | `results[i].ok = false` в формате ошибки одиночной записи; следующие элементы продолжают обрабатываться |
| Сетевой сбой на элементе | сеть | `results[i].ok = false` с текстом исключения; следующие элементы продолжают обрабатываться; состояние операции после отправки PATCH может быть неопределённым; повтор не выполняется |

## Предположения, предусловия и ограничения

- Канонический HTTP-путь частичного обновления операции и одиночный MCP-инструмент `put_transaction` доступны на профиле приёмки.
- Жёсткий прикладной лимит размера пакета в рамках задачи не вводится.
- Исполнение пакета строго последовательное; приёмка не гарантирует продолжительность вызова для больших пакетов.

## Критерий приёмки

- Одним вызовом MCP на профиле `cand` или `test` обновляются не менее двух операций, включая назначение идентификатора фонда, с результатами по каждому элементу.
- При ошибке одного элемента остальные элементы того же пакета обрабатываются согласно целевому поведению.
- Пустой пакет отклоняется исключением инструмента до разрешения сессии и до HTTP.
- Нормализованные определения свойств полей тела `put_transaction` и элемента `put_transactions` совпадают по D-04 и D-10.
- Арифметика `summary` соответствует D-10.
- Справочник доступных инструментов MCP обновлён.
- Поведение покрыто функциональным тестированием и модульными тестами.

## Функциональное тестирование

### Предусловия

- Подключение MCP `finance_api_connect` с профилем данных `cand` или `test`.
- На том же профиле доступны `put_transaction` и канонический `PATCH` операции.
- Есть не менее двух операций, пригодных для назначения идентификатора фонда.
- Есть не менее двух операций закрытого учётного периода, пригодных для проверки `allow_closed`.
- В справочнике есть фонд активного домохозяйства с интервалом, покрывающим даты выбранных операций.
- Профиль `prod` для заполнения факта прогона не использовать без отдельной ops-команды.
