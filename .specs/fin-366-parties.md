# MCP-инструменты справочника субъектов учёта

**Статус:** Утверждено (2026-09-01, rev.4).

## Назначение

- Ops не могут вести справочник субъектов учёта через MCP: инструментов нет.
- Без MCP-поверхности FIN-365 нельзя завести внешнее физическое лицо и связать его с учётом только через MCP (блокирует FIN-355).

## Входит в объём

- В объём входят инструменты MCP списка субъектов учёта профиля с опциональным фильтром типа.
- В объём входят инструменты MCP чтения субъекта учёта по идентификатору.
- В объём входят инструменты MCP создания одного субъекта учёта.
- В объём входят инструменты MCP пакетного создания субъектов учёта.
- В объём входят инструменты MCP частичного обновления отображаемого имени по идентификатору.
- В объём входят инструменты MCP пакетного частичного обновления отображаемых имён.
- В объём входят инструменты MCP удаления субъекта учёта по идентификатору.
- В объём входят инструменты MCP пакетного удаления субъектов учёта.
- В объём входят инструменты MCP чтения субъекта учёта типа `group` по домохозяйству.
- В объём входят инструменты MCP чтения субъекта учёта по члену домохозяйства через соответствие.
- В объём входят инструменты MCP установления соответствия члена домохозяйства субъекту учёта типа `person`.
- В объём входят инструменты MCP снятия соответствия члена домохозяйства.
- В объём входят обработчики и схемы инструментов в MCP-сервере.
- В объём входит модуль тонких обёрток над HTTP API субъектов учёта.
- В объём входит расширение существующего модуля домохозяйств путями чтения и соответствия.
- В объём входят unit-тесты на mock API.
- В объём входит обновление справочника доступных инструментов MCP.

## Вне объёма

- Не входят модель данных и слой сохранения субъектов учёта (FIN-364).
- Не входит HTTP API субъектов учёта (FIN-365).
- Не входит пользовательский интерфейс справочника (FIN-367).
- Не входят инструменты MCP денежного требования (FIN-355).
- Не входит начальное заполнение субъектов учёта для существующих домохозяйств и членов.
- Не входит один инструмент MCP с перечислением действия вместо отдельных инструментов.
- Не входит смена термина `accounting subject` на иной в именах инструментов MCP.

## Текущее поведение

| Область | Текущее поведение | Проблема |
| ------- | ----------------- | -------- |
| MCP субъектов учёта | Инструментов справочника нет | Ops не ведут субъектов учёта без raw HTTP |
| HTTP | FIN-365: двенадцать операций справочника и соответствий | Нужна MCP-поверхность с полным паритетом |

## Обратная совместимость

- Двенадцать новых инструментов добавляются без изменения семантики существующих инструментов MCP.
- Контракт HTTP API FIN-365 этой задачей не меняется.
- Существующие инструменты домохозяйств и членов домохозяйства FIN-240 не меняют поля ответа.

## Целевое поведение

#### Паритет поверхности субъектов учёта (D-01)

- Для публичной HTTP-поверхности FIN-365 MCP предоставляет однозначно соответствующую поверхность: каждой операции HTTP API соответствует отдельный MCP-инструмент с той же функциональной семантикой.
- MCP не исключает и не добавляет самостоятельные операции предметной области.
- Норма совпадает с [mcp-conventions.md](../../../PycharmProjects/FinancePlanningProject/standards/product/mcp-conventions.md) § Паритет HTTP API и MCP.

| Инструмент MCP | Операция HTTP | Смысл |
| -------------- | ------------- | ----- |
| `list_accounting_subjects` | `GET /api/v1/accounting-subjects` | Список |
| `get_accounting_subject` | `GET /api/v1/accounting-subjects/{subject_id}` | Чтение по идентификатору |
| `create_accounting_subject` | `POST /api/v1/accounting-subjects` | Создание одной записи |
| `create_accounting_subjects` | `POST /api/v1/accounting-subjects/batch` | Пакетное создание |
| `patch_accounting_subject` | `PATCH /api/v1/accounting-subjects/{subject_id}` | Частичное обновление по идентификатору |
| `patch_accounting_subjects` | `PATCH /api/v1/accounting-subjects` | Пакетное частичное обновление |
| `delete_accounting_subject` | `DELETE /api/v1/accounting-subjects/{subject_id}` | Удаление по идентификатору |
| `delete_accounting_subjects` | `DELETE /api/v1/accounting-subjects` | Пакетное удаление |
| `get_household_accounting_subject` | `GET /api/v1/households/{household_id}/accounting-subject` | Чтение группы по домохозяйству |
| `get_household_member_accounting_subject` | `GET /api/v1/household-members/{household_member_id}/accounting-subject` | Чтение по члену через соответствие |
| `link_household_member_accounting_subject` | `POST /api/v1/household-members/{household_member_id}/accounting-subject-link` | Установление соответствия |
| `unlink_household_member_accounting_subject` | `DELETE /api/v1/household-members/{household_member_id}/accounting-subject-link` | Снятие соответствия |

#### Правила набора (D-02)

- Создание, изменение и удаление разведены по разным инструментам; индивидуальные и пакетные операции — тоже.
- Идентификатор субъекта учёта при создании задаёт слой сохранения; клиент MCP поле `id` при создании не передаёт.
- Один инструмент с перечислением действия не используется.
- Доменные правила тел, атомарности пакетов и кодов ошибок наследуются из FIN-365 без дублирования в MCP.

#### Общий конвейер (D-03)

```
1. получить сессию API (профиль данных, базовый URL)
2. проверить аргументы MCP до HTTP
3. собрать путь, параметры запроса и тело
4. выполнить вызов метода GET, POST, PATCH или DELETE
5. при коде HTTP 200 или 201 ожидать тело ответа и обернуть сущность или коллекцию в конверт ok / profile / base
6. при коде HTTP 204 не ожидать тела ответа и вернуть только конверт ok / profile / base
7. иначе вернуть ошибку инструмента с телом ответа API
8. сетевые сбои пробросить без дополнительной обёртки
```

- Порядок шагов фиксирован.
- Успех операции определяется кодом HTTP, а не наличием или отсутствием тела в ответе.
- Доменные инварианты субъекта учёта не дублируются в MCP.

#### Модуль и регистрация (D-04)

- Логика обёрток CRUD и пакетов размещается в `scripts/accounting_subjects.py`.
- Логика путей домохозяйства и члена домохозяйства размещается в существующем `scripts/households.py`.
- Обработчики и схемы инструментов регистрируются в `server.py`.
- Справочник доступных инструментов обновляется в `mcp-gaps.md`.
- Метка `mcp-gap` снимается с FIN-366 после поставки инструментов.

#### Профиль данных и базовый URL (D-05)

- Необязательные аргументы `profile` и `base` наследуют поведение FIN-293 D-07: отсутствие ключа — значение из сессии MCP; для `profile` по умолчанию `prod`; пустая строка после `strip` даёт `ValueError` до HTTP.
- Успешный ответ всегда содержит эффективные `profile` и `base`.

#### JSON Schema MCP и обработчик (D-24)

- JSON Schema каждого инструмента проверяет: тип корневого объекта аргументов; тип каждого **переданного** ключа; тип каждого элемента переданных массивов; `additionalProperties: false` в корне и в объектах элементов пакетных массивов.
- JSON Schema **не** задаёт `required`, `minItems`, `minLength` и обязательность полей внутри элементов пакета.
- Колонка «Обяз.» в таблицах D-09–D-20 означает обязательность для успешного вызова; проверку выполняет обработчик по D-06, а не JSON Schema.
- Элементы `accounting_subjects` в аргументах — object; неверный тип элемента (например, строка вместо object) отклоняется JSON Schema до обработчика.
- Элементы `ids` в аргументах — string; неверный тип элемента (например, число вместо string) отклоняется JSON Schema до обработчика.
- Для полей и элементов массивов, где явный `null` должен приводить к `ValueError` обработчика (D-07), JSON Schema включает `null` в допустимый тип (например, `"type": ["string", "null"]`, `"type": ["array", "null"]`).
- Неизвестный ключ аргумента или элемента пакета даёт ошибку JSON Schema до обработчика; HTTP не вызывается.
- Передача `id` при создании субъекта учёта — неизвестный ключ → ошибка JSON Schema (не молчаливое игнорирование).

#### Валидация до HTTP (D-06)

- Обработчик выполняет структурную проверку после JSON Schema (D-24).
- До HTTP обработчик проверяет: наличие обязательных ключей успешного вызова; запрет `null` там, где D-07 требует `ValueError`; непустые пакетные массивы; наличие обязательных ключей в элементах пакета.
- Для создания одной записи обязательны ключи `subject_type` и `display_name`; значения передаются в HTTP без нормализации MCP.
- Ключ `household_id` при создании попадает в JSON тела только если присутствует в аргументах MCP.
- Для частичного обновления одной записи ключ `display_name` обязателен; значение передаётся в HTTP без нормализации MCP.
- Для пакетного создания присутствует непустой список `accounting_subjects`; у каждого элемента присутствуют ключи `subject_type` и `display_name`.
- Для пакетного обновления присутствует непустой список `accounting_subjects`; у каждого элемента присутствуют ключи `id` и `display_name`.
- Для пакетного удаления присутствует непустой список `ids`; каждый элемент — непустая строка.
- Для установления соответствия обязательны ключи `subject_id` (тело HTTP) и `household_member_id` (сегмент пути); значения передаются в HTTP без нормализации MCP.
- Для списка ключ `subject_type` попадает в query только если присутствует в аргументах MCP.
- Идентификатор в **сегменте пути** (`subject_id` в get/patch/delete, `household_id`, `household_member_id`): пустая строка даёт `ValueError` до HTTP.
- `subject_id` в **теле** установления соответствия (D-19): обработчик проверяет только наличие ключа и тип; пустая строка передаётся в HTTP → `validation_error` (не `ValueError` MCP).
- Нарушение правил D-06 даёт `ValueError` без вызова API.
- Пустое `display_name`, неверный UUID, недопустимый `subject_type`, конфликты соответствия и атомарность пакета проверяет только backend; MCP пробрасывает ответ API без смены `error.code`.

#### Нормализация входа MCP (D-22)

- MCP не нормализует поля тела и пути субъекта учёта: `subject_type`, `display_name`, `household_id`, `subject_id`, `household_member_id`, фильтр `subject_type`.
- Удаление крайних символов `U+0020 SPACE`, проверка UUID, доменные отказы и `details.index` пакетов — только FIN-365 D-04, D-06, D-08, D-12–D-17, D-18.
- Исключение: аргументы `profile` и `base` — по D-05 (пустая строка после `strip` даёт `ValueError` до HTTP).
- MCP не исправляет неканонический UUID без дефисов и не удаляет табуляцию или неразрывный пробел из `subject_type`.

#### Отсутствие ключа и явное обнуление (D-07)

- Ключ, отсутствующий в аргументах MCP, не попадает в JSON тела запроса и не формирует query-параметр.
- Пустая строка не преобразуется в `null`.
- Значение по умолчанию параметра в коде не смешивает «ключ не передан» и «ключ передан со значением `null`».
- Отсутствие ключа и явный `null` — различные состояния.
- Явный `null` для любого известного аргумента инструмента, для которого контракт MCP не предусматривает `null`, отклоняется обработчиком до HTTP через `ValueError` (после прохождения JSON Schema D-24).
- Примеры: `household_id: null` при создании; `subject_type: null`; `display_name: null`; `profile: null`; `base: null`; `accounting_subjects: null`; `ids: null`; `null` внутри элемента пакета — `ValueError` обработчика, HTTP не вызывается.

#### Разворачивание ответа HTTP (D-25)

- MCP не вкладывает HTTP-обёртку коллекции во второй уровень с тем же именем.
- Список: HTTP `{"accounting_subjects": […]}` → MCP `{"ok": true, "profile": …, "base": …, "accounting_subjects": […]}`.
- Пакетное создание/обновление с телом: HTTP `{"accounting_subjects": […]}` → MCP тот же ключ `accounting_subjects` на верхнем уровне ответа инструмента рядом с `ok` / `profile` / `base`.
- Одиночное чтение/создание/обновление: HTTP-модель D-03 → MCP `accounting_subject` на верхнем уровне.
- Успех HTTP 204: только `ok` / `profile` / `base` без ключей сущности.

#### Инварианты (D-08)

- MCP не ослабляет инварианты HTTP API FIN-365.
- Тело запроса содержит только явно переданные ключи аргументов.
- Ответ REST не нормализуется: только конверт `ok` / `profile` / `base` и ключ сущности или коллекции; при коде HTTP 204 ключ сущности отсутствует.
- Имена ключей коллекций в успешном ответе совпадают с HTTP: `accounting_subjects` для списков и пакетных ответов с телом; `accounting_subject` для одиночной модели.

#### Список субъектов учёта (D-09)

| Поле | Тип | Обяз. | Описание |
| ---- | --- | ----- | -------- |
| `profile` | string | нет | Профиль данных; по умолчанию `prod` |
| `base` | string | нет | Базовый URL API; по умолчанию из сессии |
| `subject_type` | string | нет | Фильтр типа: `person`, `organization` или `group` |

- При успехе ответ инструмента содержит `ok: true`, профиль, базовый URL и коллекцию `accounting_subjects`.
- Пустой список допустим и сохраняет `ok: true`.
- Успех соответствует ответу API с кодом HTTP 200.
- Порядок элементов в `accounting_subjects` совпадает с FIN-365 D-04: стабильная сортировка по `id` по возрастанию (лексикографически по каноническому UUID с дефисами).
- MCP не пересортировывает и не фильтрует ответ API.
- Неизвестный тип фильтра даёт ошибку инструмента по ответу API с кодом HTTP 422 и кодом ошибки `invalid_subject_type`.
- Пустой `subject_type` после нормализации FIN-365 D-04 даёт ошибку инструмента с кодом HTTP 422 и кодом ошибки `validation_error` (не `ValueError` MCP).

#### Чтение субъекта учёта (D-10)

| Поле | Тип | Обяз. | Описание |
| ---- | --- | ----- | -------- |
| `profile` | string | нет | Профиль данных |
| `base` | string | нет | Базовый URL API |
| `subject_id` | string | да | Идентификатор субъекта учёта в пути |

- При успехе ответ инструмента содержит `ok: true` и объект `accounting_subject`.
- Успех соответствует ответу API с кодом HTTP 200.
- Отсутствие субъекта учёта даёт ошибку инструмента с кодом HTTP 404 и кодом ошибки `subject_not_found`.
- Синтаксически неверный UUID даёт ошибку инструмента с кодом HTTP 422 и кодом ошибки `validation_error`.

#### Создание субъекта учёта (D-11)

| Поле | Тип | Обяз. | Описание |
| ---- | --- | ----- | -------- |
| `profile` | string | нет | Профиль данных |
| `base` | string | нет | Базовый URL API |
| `subject_type` | string | да | `person`, `organization` или `group` |
| `display_name` | string | да | Отображаемое имя |
| `household_id` | string | нет | Идентификатор домохозяйства; только для `group` |

- Успешное создание соответствует ответу API с кодом HTTP 201.
- При успехе ответ инструмента содержит `ok: true` и объект `accounting_subject` с выданным идентификатором.
- Поле `id` в аргументах создания не передаётся.

```json
{
  "ok": true,
  "profile": "cand",
  "base": "http://127.0.0.1:8001",
  "accounting_subject": {
    "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
    "subject_type": "person",
    "display_name": "Arkady",
    "created_at": "2026-09-01T10:00:00.000Z",
    "updated_at": "2026-09-01T10:00:00.000Z"
  }
}
```

#### Пакетное создание (D-14)

| Поле | Тип | Обяз. | Описание |
| ---- | --- | ----- | -------- |
| `profile` | string | нет | Профиль данных |
| `base` | string | нет | Базовый URL API |
| `accounting_subjects` | array | да | Элементы с полями как у D-11 |

- Успех соответствует ответу API с кодом HTTP 201.
- При успехе ответ инструмента содержит `ok: true` и коллекцию `accounting_subjects`.

- Порядок элементов в ответе совпадает с порядком входного массива (FIN-365 D-09).
- Повтор `id` в одном пакете даёт ошибку инструмента с кодом HTTP 422 и кодом ошибки `validation_error` до транзакции.
- MCP не реализует собственную атомарность; полностью наследует контракт FIN-365 D-09 и D-16.
- Доменная ошибка элемента внутри транзакции — первый отказ с `error.details.index` по FIN-365 D-09.

#### Пакетное удаление (D-16)

| Поле | Тип | Обяз. | Описание |
| ---- | --- | ----- | -------- |
| `profile` | string | нет | Профиль данных |
| `base` | string | нет | Базовый URL API |
| `ids` | array | да | Список UUID субъектов учёта |

- Успех соответствует ответу API с кодом HTTP 204; ответ инструмента — `ok: true`, профиль и базовый URL без коллекции.
- Повтор одного UUID в `ids` даёт ошибку инструмента с кодом HTTP 422 и кодом ошибки `validation_error` до транзакции.
- MCP не реализует собственную атомарность; полностью наследует контракт FIN-365 D-11 и D-16.
- При доменном отказе внутри транзакции последующие элементы не проверяются; `error.details.index` равен индексу первого неуспешного элемента.

#### Чтение группы по домохозяйству (D-17)

| Поле | Тип | Обяз. | Описание |
| ---- | --- | ----- | -------- |
| `profile` | string | нет | Профиль данных |
| `base` | string | нет | Базовый URL API |
| `household_id` | string | да | Идентификатор домохозяйства в пути |

- При успехе ответ инструмента содержит `ok: true` и объект `accounting_subject`.
- Успех соответствует ответу API с кодом HTTP 200.
- Порядок проверок совпадает с FIN-365 D-12: сначала существование домохозяйства, затем представление группы.
- Отсутствие домохозяйства даёт ошибку инструмента с кодом HTTP 404 и кодом ошибки `household_not_found`; `get_subject_by_household` не вызывается.
- Домохозяйство без представления даёт ошибку инструмента с кодом HTTP 404 и кодом ошибки `subject_not_found`.

#### Чтение по члену домохозяйства (D-18)

| Поле | Тип | Обяз. | Описание |
| ---- | --- | ----- | -------- |
| `profile` | string | нет | Профиль данных |
| `base` | string | нет | Базовый URL API |
| `household_member_id` | string | да | Идентификатор члена в пути |

- При успехе ответ инструмента содержит `ok: true` и объект `accounting_subject`.
- Успех соответствует ответу API с кодом HTTP 200.
- Порядок проверок совпадает с FIN-365 D-13: сначала существование члена, затем соответствие.
- Отсутствие члена даёт ошибку инструмента с кодом HTTP 404 и кодом ошибки `household_member_not_found`; `get_subject_by_member` не вызывается.
- Член без соответствия даёт ошибку инструмента с кодом HTTP 404 и кодом ошибки `subject_not_found`.

#### Установление соответствия (D-19)

| Поле | Тип | Обяз. | Описание |
| ---- | --- | ----- | -------- |
| `profile` | string | нет | Профиль данных |
| `base` | string | нет | Базовый URL API |
| `household_member_id` | string | да | Идентификатор члена в сегменте пути |
| `subject_id` | string | да | Идентификатор субъекта в теле HTTP (не сегмент пути) |

- Успех соответствует ответу API с кодом HTTP 204; ответ инструмента — `ok: true`, профиль и базовый URL без объекта субъекта учёта.
- Перед `link_member_subject` HTTP-слой подтверждает существование члена; отсутствие члена даёт `household_member_not_found` до доменных отказов соответствия.
- После успешной схемы HTTP и подтверждения члена доменные отказы проверяются в порядке FIN-365 D-14 и останавливаются на первом сработавшем шаге:

1. Субъект учёта отсутствует → HTTP 404, `subject_not_found`.
2. Тип субъекта учёта не равен `person` → HTTP 422, `invalid_subject_type`.
3. У члена уже есть соответствие → HTTP 409, `member_subject_link_exists`.
4. У этого физического лица уже есть соответствие с другим членом того же домохозяйства → HTTP 409, `household_person_link_exists`.

- MCP не меняет этот порядок и не вводит собственных кодов ошибок.

#### Снятие соответствия (D-20)

| Поле | Тип | Обяз. | Описание |
| ---- | --- | ----- | -------- |
| `profile` | string | нет | Профиль данных |
| `base` | string | нет | Базовый URL API |
| `household_member_id` | string | да | Идентификатор члена в пути |

- Успех соответствует ответу API с кодом HTTP 204; ответ инструмента — `ok: true`, профиль и базовый URL без объекта субъекта учёта.
- Порядок проверок совпадает с FIN-365 D-15: сначала существование члена, затем наличие соответствия.
- Отсутствие члена даёт ошибку инструмента с кодом HTTP 404 и кодом ошибки `household_member_not_found`; `unlink_member_subject` не вызывается.
- Член без соответствия даёт ошибку инструмента с кодом HTTP 404 и кодом ошибки `member_subject_link_not_found`.

#### Конкурентные изменения (D-23)

- Пути D-17–D-20 наследуют FIN-365 D-12a: различение кодов ошибки гарантируется для состояния активного профиля на момент предварительной проверки HTTP-слоя.
- MCP не добавляет транзакционной обёртки поверх двухшаговых HTTP-путей и не обещает согласованность между предварительным чтением и последующей операцией FIN-364.

#### Ошибки (D-21)

- Ответ API с кодом, отличным от успеха операции, даёт `RuntimeError` через `format_api_error`.
- Мягкий ответ вида `{ "ok": false }` без исключения не используется.
- Все доменные ошибки полностью наследуются из FIN-365 D-18, включая `accounting_subject_store_busy` (HTTP 503) для пакетов; MCP не вводит собственных кодов ошибок справочника субъектов учёта.
- Приоритет ошибок пакетов и путей соответствия не выводится в MCP: действуют FIN-365 D-07, D-09, D-11, D-14, D-15, D-17.
- Ошибка JSON Schema (D-24): неизвестный ключ, несовместимый тип переданного значения — до обработчика; HTTP не вызывается.
- Локальная валидация обработчика (D-06, D-07): `ValueError` без вызова API.
- Ошибка разрешения сессии наследует поведение существующих инструментов MCP.
- Сетевой сбой пробрасывается без дополнительной обёртки.

| Класс | Источник | HTTP вызывается | Исключение / ответ |
| ----- | -------- | --------------- | ------------------ |
| JSON Schema | неизвестный ключ, неверный тип переданного значения (D-24) | нет | ошибка схемы до обработчика |
| Локальная валидация | обработчик: обязательные ключи, `null`, пустые пакеты, пустой идентификатор в сегменте пути (D-06, D-07) | нет | `ValueError` |
| Сессия / конфигурация | `finance_api_connect` / `get_session` | нет | как у существующих tools |
| Домен HTTP | ответ API 4xx/5xx с `error.code` | да | `RuntimeError` с телом API |
| Неожиданный HTTP | иной код, в том числе незаявленный `2xx` | да | `RuntimeError` |
| Сеть | транспорт | да | исходное исключение |

## Предположения, предусловия и ограничения

- HTTP API FIN-365 rev.5 развёрнут и доступен на целевом профиле приёмки.
- Одиночные операции FIN-364 rev.8 доступны в постоянной базе данных приложения.
- Операции чтения домохозяйства и члена домохозяйства FIN-240 доступны HTTP-слою FIN-365 для предварительных проверок путей соответствия.

## Критерий приёмки

- Справочник субъектов учёта доступен через MCP для всех двенадцати операций публичной HTTP-поверхности FIN-365 согласно целевому поведению.
- Ops могут создать внешнее физическое лицо, прочитать его, переименовать, удалить и получить список только через MCP.
- Ops могут установить и снять соответствие члена домохозяйства субъекту учёта типа `person` только через MCP.
- Доменные ошибки API пробрасываются в ошибку инструмента без потери кода ошибки.
- Поведение покрыто unit-тестами и функциональным тестированием на профиле `cand` или `test`.
- Метка `mcp-gap` снята с FIN-366 после поставки инструментов.
